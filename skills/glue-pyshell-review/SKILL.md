# AWS Glue Python Shell コードレビュー

Python Shell ジョブは「1 台のマシンで動く普通の Python スクリプト」である。Spark の分散処理の知識はいらない代わりに、次のような壊れ方をする。

- 入力が想定より大きくなり、**1 台のメモリ（1 GB または 16 GB）に載らず OOM** で落ちる
- 例外を握りつぶして、**処理に失敗したのにジョブが「成功」になり、誰も気づかない**
- ジョブブックマークがないため、**再実行や失敗後の再処理で出力が重複・欠損**する
- boto3 の使い方（ページネーション漏れ、リトライなし）で、**件数が増えたときに黙って一部だけ処理**する

このレビューの目的は、これらを**ジョブの規模に見合った範囲で**見つけて是正することにある。
Python Shell を選ぶのは、小規模で単純な処理だからである。実行方式は実装前に決まっている前提とし、レビューでは別の方式への移行を論じない。大規模ジョブ向けの重い仕組み（テーブル形式の導入、細かいメトリクス設計など）も当然のように求めない。
文法やスタイルの指摘は二の次でよい。「失敗が検知できない」「再実行で壊れる」「データ量が増えると落ちる・黙って取りこぼす」を優先する。

コードだけでは確定できないこと（実際のデータ量、ジョブ定義の設定、上流の仕様）は断定せず、「〜の可能性がある。〜で確認を」のように確認方法を添える。

## レビュー手順

### 1. ジョブの前提を把握する

コードと周辺ファイル（IaC、ジョブ定義、README など）から以下を特定する。不明なものは推測した前提としてレビュー冒頭に明記する。

- **ジョブタイプと実装の食い違い**: ジョブ定義（コマンド名 `pythonshell`）とコードの両方を見て、次のように判断する
  - **Python Shell ジョブなのに、コードに Spark の実装がある**（`pyspark` の import、`GlueContext` / `SparkSession` / `SparkContext` の生成、DynamicFrame の利用など）: 🚨High として指摘する。Python Shell の環境には Spark がないため、import やコンテキスト生成の時点でジョブが失敗する可能性が高い。Spark ジョブのコードを流用したときの消し忘れなど、一部だけ残っているケースも同様に扱う。改善案は「Spark を使わない実装に置き換える」とし、どこを置き換えるかを示す
  - **ジョブ定義が見当たらず、コード全体が Spark 前提で書かれている**: Spark ETL ジョブのコードである可能性が高い。「Python Shell ジョブとして動かすなら上記の High に当たる。Spark ETL ジョブならこのスキルの対象外」と伝え、どちらなのかを確認する
  - `awsglue.utils.getResolvedOptions` は Python Shell でも使える。`awsglue` の import があるだけで Spark の実装と判断しない
- **DPU と Python のバージョン**: DPU 0.0625（メモリ 1 GB）か 1（16 GB）か。Python のバージョン
- **使えるライブラリとそのバージョン**: ジョブ定義の `library-set`（`analytics` / `none`）と、`--additional-python-modules` などで追加・更新しているライブラリ。`analytics` に同梱されるライブラリ（pandas、boto3 など）はバージョンが固定されていて最新ではない。コードが使っている API や引数がそのバージョンで使えるかを確認してから、指摘や改善案の前提にする
- **処理の種類**: S3 のファイル変換 / 外部 API 連携 / Athena・Redshift へのクエリ発行 / AWS リソースの操作 など
- **入出力と想定データ量**: 1 回の実行で扱うファイルの数とサイズ、レコード数。分からなければ「ファイル 1 つが数百 MB〜数 GB になりうる」と仮定して、メモリ上限に対して評価する。ただし、この仮定は見落としを防ぐための安全側の置き方であり、実データの規模ではない。**仮定だけを根拠に 🚨High にしない**。メモリに関する指摘の重要度は、コード・ジョブ定義・README などから確認できる実際の規模と実行条件（DPU など）に基づいて決める。規模が確認できない場合は、「データ量が〜を超えると OOM になりうる。実際の規模を確認を」のように条件付きで書き、確認事項として扱う
- **実行のされ方**: スケジュール / イベント起動 / 手動、リトライ回数、同時実行数

### 2. 処理の流れを「メモリ」と「失敗」の視点で追う

上から順に、以下を意識して読む。

- どこでデータを**丸ごとメモリに載せているか**（`read()`、`pd.read_csv`、リストへの蓄積など）
- どこで**外部呼び出し**（S3、API、DB）をしているか。失敗・スロットリング時にどうなるか
- **途中で落ちたら**どこまで出力が残るか。**もう一度実行したら**どうなるか
- 例外が最終的に**ジョブの失敗として表に出るか**

### 3. チェックリストで確認する

`references/pyshell-checklist.md` を読み、該当する観点を確認する。チェックリストはよくある失敗パターン集であり、全項目を指摘として埋める必要はない。
リストにない問題でも「メモリに載り切らない」「失敗が隠れる」「再実行で壊れる」「件数が増えると黙って取りこぼす」に当てはまるなら指摘する。

### 4. 指摘を書く

各指摘は以下のテンプレートで書く。改善後のコード例は、コードから前提が読み取れて安全に示せる場合に添える。ジョブ設定・インフラ・要件など、コードの外の情報に依存する指摘では、コード例の代わりに「確認すべきこと」と「改善の方針」を書く。
「何が起きるか（例: ファイルが 2 GB を超えると 1 GB のメモリに載らず OOM）」を具体的に説明し、次に同じコードを書くときの学びになるようにする。

````md
## <!-- 指摘内容の要約 -->

- **重要度**: [ 🚨High / ⚠️Medium / ℹ️Low / 💡Suggestion ]
- **箇所**: `path/to/job.py:42`
- **観点**: <!-- 例: メモリ / 失敗検知 / 再実行 / boto3 -->

**詳細**

<!-- 何が問題で、本番で何が起きるか -->

**改善案**

```python
# 修正後のコード（安全に示せる場合）
```

<!-- コード例を示せない場合は、確認事項と改善方針を書く -->

**補足**

<!-- トレードオフ、前提条件、同様の箇所が他にあればそのパス -->
````

重要度の目安:

- **🚨High**: ジョブが動かない、失敗が検知されない、または再実行・失敗でデータの欠損・重複が起きる。確認できる実際のデータ量でメモリ上限を超えうる（例: Python Shell ジョブに Spark の実装が残っている、例外を握りつぶして正常終了、ページネーションなしで 1,000 件を超えた分を取りこぼす、低レベル API の `UnprocessedItems` を再送していない、処理前に入力を削除する）
- **⚠️Medium**: 動くが、データ量の増加やスロットリングで不安定になる・遅くなる（例: 大量の API 呼び出しに対して実効のリトライ方針が見合っていない、全列を読み込んでいる）
- **ℹ️Low**: 影響は小さいが改善した方がよい（例: 環境ごとに変わる値のハードコード、障害調査に必要な情報（処理件数・失敗件数など）がログに出ていない）
- **💡Suggestion**: 品質・保守性の提案（例: `print` から `logging` への置き換え）

書き方の形式（`print` を使っている、`Config` でリトライを明示していない、IAM ポリシーに `*` がある など）だけを根拠に指摘しない。その書き方によって**何が起きるか**を説明できる場合に指摘する。

### 5. まとめる

レビューの最後に以下を書く。

- 前提として置いた仮定（DPU、データ量、実行のされ方）
- 重要度別の件数
- 最も効果の大きい改善 1〜3 点（どれから直すべきか）

問題が見当たらない観点まで列挙する必要はない。指摘ゼロなら、その旨と確認した主な観点を簡潔に書けばよい。
