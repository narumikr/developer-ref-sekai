# Terraformの実装ベストプラクティス

## はじめに

本記事は、はじめてTerraformでの実装に取り組む方を対象としています。

Terraformの経験者にとっては当たり前のポイントでも、知らないまま実装を進めてしまうと、後から大幅な手戻りが発生することがあります。私自身が初めて対応したときに実際にやってしまったミスをまとめることで、同じ思いをする方を一人でも減らせればと思い執筆しました。

作成するクラウドサービスや構成が決まり、これから実装設計に入るというタイミングで、一度立ち止まって読んでいただけると幸いです。

HashiCorpは、Terraformの実行やstate管理をSaaSとして提供する「HCP Terraform」（2024年に「Terraform Cloud」から名称変更）を提供していますが、今回はスコープ外とします。

## すべてのリソースを1つのファイルに書いてしまう

### よくある状態

はじめてTerraformを書くときは、「まずは動くものを作りたい」という焦りや、「リソース間の依存関係は同じ場所で管理したほうが良いのではないか」という思い込みから、main.tf の中にVPC、サブネット、セキュリティグループ、ECS、RDSなどをすべて書き連ねてしまうこともあるかもしれません

```text
.
└── main.tf   # すべてのリソースがここに入っている
```

小規模な検証環境であれば、これでも問題なく動きます。ただし、構成が大きくなったり環境が増えたりすると、後から整理するのに大きな手間がかかります。

### 1ファイル構成のメリット

1ファイル構成が常に悪いわけではありません。次のような場面では、むしろ適しています。

- 動作検証やPoCなど、短期間で作って捨てる環境
- リソースが数個〜十数個程度で、今後も増える予定がない
- Terraformの学習目的で、まず全体の流れを掴みたい

ファイルを行き来しなくても全体を見渡せるので、学習初期には分かりやすい構成です。

### 整理には2段階ある

ここで混同しやすいのが「ファイル分割」と「Module化」です。この2つは別物です。

| | ファイル分割 | Module化 |
|---|---|---|
| やること | 同じディレクトリ内で `.tf` ファイルを分ける | ディレクトリを分け、`module` ブロックで呼び出す |
| Terraformからの見え方 | 1つのファイルと同じ扱い（全ファイルが結合されて読まれる） | 独立した部品として扱われる |
| 主な目的 | 可読性 | 再利用・責務の分離 |

```text
.
├── versions.tf    # terraform / provider のバージョン指定
├── providers.tf   # provider 設定
├── variables.tf   # 入力変数
├── outputs.tf     # 出力値
├── network.tf     # VPC、サブネットなど
├── ecs.tf         # ECS関連
└── rds.tf         # RDS関連
```

### Module構成とは

Moduleとは、**関連するリソースをひとまとめにし、入力（variable）と出力（output）を持たせた部品**のことです。プログラミングでいう関数に近いイメージです。

実は、`terraform apply` を実行するディレクトリ自体も「ルートモジュール」と呼ばれるModuleです。そこから呼び出される部品を「子モジュール」と呼びます。

#### 子モジュールの例

```text
modules/network/
├── main.tf
├── variables.tf
└── outputs.tf
```

```hcl
# modules/network/variables.tf
variable "name" {
  type = string
}

variable "vpc_cidr" {
  type = string
}
```

```hcl
# modules/network/main.tf
resource "aws_vpc" "this" {
  cidr_block = var.vpc_cidr

  tags = {
    Name = var.name
  }
}
```

```hcl
# modules/network/outputs.tf
output "vpc_id" {
  value = aws_vpc.this.id
}
```

#### 呼び出し側（ルートモジュール）

```hcl
module "network" {
  source = "../../modules/network"

  name     = "myapp-dev"
  vpc_cidr = "10.0.0.0/16"
}

# 子モジュールの output は module.<名前>.<output名> で参照する
resource "aws_security_group" "app" {
  vpc_id = module.network.vpc_id
  # ...
}
```

Moduleの中のリソースは外から直接参照できません。外に渡したい値は `output` で明示的に公開する必要があります。この「入口と出口を明確にする」点が、Module化の大きな価値です。

### どの規模になったらModule化すべきか

公式に「何リソース以上ならModule化」という基準はありません。私は以下のどれかに当てはまったらModule化を検討する、という目安にしています。

- **dev / stg / prod など複数環境を作る**
  - 最も分かりやすい基準です。環境ごとにコピペすると、修正漏れや環境差分の原因になります。
- **同じパターンのリソース群を何度も書いている**
  - 例：ECSサービスを複数作る、S3バケットを同じ設定で複数作る
- **複数人で開発する**
  - 担当範囲を分けやすくなり、レビューもしやすくなります。
- **ファイル分割しても見通しが悪い**
  - どのリソースがどれに依存しているか追えなくなってきたら、責務を切り出すタイミングです。

逆に、単一環境で、今後も再利用の予定がないなら、無理にModule化せずファイル分割で十分なこともあります。

### どういった単位でModuleを切るべきか

基本の考え方は **「一緒に作られ、一緒に変更されるもの」をまとめる** ことです。

#### よくある分け方の例（AWS）

| Module | 含むリソースの例 |
|---|---|
| network | VPC、サブネット、ルートテーブル、IGW、VPCエンドポイント |
| security | セキュリティグループ、IAMロール（共通で使うもの） |
| ecs-service | ECSサービス、タスク定義、ターゲットグループ、ロググループ |
| database | RDS、サブネットグループ、パラメータグループ |

#### 避けたい切り方

- **1リソース = 1Module**
  - `aws_s3_bucket` をただ包んだだけのModuleは、引数を素通しするだけで価値がありません。管理するファイルが増えるだけです。
- **何でも入りの巨大Module**
  - 1ファイル構成と同じ問題がModuleの中で起きます。
- **AWSのサービス種別だけで機械的に分ける**
  - 「EC2用」「IAM用」のように分けると、1つの機能を変更するために複数Moduleを触ることになります。機能や責務の単位で考えるのがおすすめです。

### ディレクトリ構成の例

環境ごとにルートモジュールを分け、共通部品を `modules/` に置く構成がよく使われます。

```text
.
├── modules/
│   ├── network/
│   ├── ecs-service/
│   └── database/
└── envs/
    ├── dev/
    │   ├── main.tf        # modules を呼び出す
    │   ├── variables.tf
    │   ├── terraform.tfvars
    │   └── backend.tf     # 環境ごとに state を分ける
    ├── stg/
    └── prod/
```

環境ごとにディレクトリを分けると、stateファイルも環境ごとに分かれます。そのため、「devを触ったつもりがprodに影響した」という事故を防ぎやすくなります。

## stateファイルをローカルで管理してしまう

### よくある状態

ローカル環境で `terraform init` → `terraform apply` を実行すると、作業ディレクトリに `terraform.tfstate` というファイルが作られます。何も設定しなければ、このファイルは **自分のPCの中だけ** に保存されます。

```text
.
├── main.tf
├── terraform.tfstate         # ← apply すると作られる
└── terraform.tfstate.backup
```

私がやってしまったこととして、ステートファイルはコマンド実行によって生成されたものかつ.gitignoreで管理外にしていることから`node_module`のように再生成できる成果物くらいにしか思っていませんでした。

### そもそもstateファイルとは

stateファイルは、**Terraformのコードと実際のクラウド上のリソースを対応づける台帳** です。

- `aws_vpc.main` が、実際にはどのVPC ID（`vpc-0abc...`）なのか
- 前回の `apply` で、どの属性値で作成したのか

Terraformは `plan` のたびに「コード」「stateファイル」「実際のリソース」の3つを比較して、差分を計算しています。そのため、**stateファイルを失うと、Terraformは自分が作ったリソースを認識できなくなります**。

### ローカル管理で起きる問題

#### stateファイルが失われる

PCの故障や作業ディレクトリの削除でstateファイルが消えると、Terraformからはリソースが1つも存在しないように見えます。この状態で `apply` すると、同じリソースを新規作成しようとして名前の重複でエラーになるか、二重に作成されてしまいます。

復旧するには、既存リソースを1つずつ `terraform import` で取り込み直す必要があります。リソース数が多いと非常に大変な作業です。

#### チームで共有できない

Aさんのstateファイルは、Aさんの手元にしかありません。BさんがコードをpullしてAさんと同じ環境に `apply` すると、Bさんの手元には空のstateしかありません。そのため、同じリソースをもう一度作ろうとしてしまいます。

#### 同時実行で壊れる

stateファイルを共有フォルダなどで共有していたとしても、2人が同時に `apply` するとstateファイルが上書きされ、内容が壊れることがあります。

### S3バックエンドとは

Terraformでは、stateファイルの保存先を「バックエンド」と呼びます。S3バックエンドを使うと、stateファイルをS3バケットに保存できます。

| | ローカル | S3バックエンド |
|---|---|---|
| 保存場所 | 自分のPC | S3バケット |
| チームでの共有 | できない | できる |
| 同時実行の防止（ロック） | なし | あり |
| 誤って壊したときの復元 | 困難 | バージョニングで過去の状態に戻せる |
| 暗号化 | なし | 保存時に暗号化できる |

### S3バックエンドでは何が変わるのか

S3バックエンドを設定すると、stateファイルの置き場所が自分のPCからS3に変わります。ただ、変わるのは置き場所だけではありません。Terraformの動き方そのものが変わります。

**stateファイルが手元に作られなくなる**
`terraform init` の時点で、Terraformは「このプロジェクトのstateはS3のこの場所にある」と認識します。以降、作業ディレクトリに `terraform.tfstate` は作られません。PCが壊れても、ディレクトリを消しても、stateはS3に残り続けます。

**plan / apply のたびにS3のstateを参照する**
`plan` や `apply` を実行すると、TerraformはS3から最新のstateを読み込んで差分を計算します。`apply` が終わると、更新したstateをS3に書き戻します。誰がどのPCから実行しても、同じ1つのstateを見ることになります。そのため、「Aさんの手元にしかstateがない」という問題は起きません。

**実行中はロックがかかる**
ロックを有効にしておくと、`plan` や `apply` の実行中はS3上のstateにロックがかかります。その間に別の人が実行しようとしても、「ロック中」のエラーで止まります。2人が同時に apply してstateが壊れる、という事故を仕組みで防げます。

**過去のstateに戻せる**
S3バケットのバージョニングを有効にしておけば、stateが更新されるたびに過去のバージョンが残ります。万が一stateがおかしくなっても、正常だった時点のstateに戻せます。

## さいごに

本記事では、初心者がやってしまいがちなミスを2つ紹介しました。

- すべてのリソースを1つのファイルに書いてしまう
- stateファイルをローカルで管理してしまう

作り始めの段階では問題なく動きます。そのため、ミスに気づくのは環境が増えたり、チームで開発するようになったりと、ある程度実装が進んでからになりがちです。その時点で直そうとすると、既存リソースの移行やstateの移し替えなど、本来やらなくてよかった作業が発生してしまいます。

知らないことはいざ対応時に設計に組み込むことは不可能です。

この記事によってはじめてTerraformを扱おうとする人の助けになることを願います。
