## 1. Driver へのデータ集約

Driver は 1 ノードしかないため、分散データを Driver に集めると、データ量に比例してメモリを使い OOM になる。

| 要注意の呼び出し | 問題 | 代替 |
| --- | --- | --- |
| `df.collect()` | 全件を Driver に転送 | 変換は DataFrame API のまま行い、書き込みは Executor から行う |
| `df.toPandas()` | 全件を Driver の pandas に変換 | Spark の関数で処理する |
| `dyf.toDF().collect()` で行ループ | Driver 上の逐次処理になる | `withColumn` / `when` / `groupBy` などで列単位に処理する |
| `df.take(n)` / `limit(n).collect()` で n が大きい | 同上 | 確認用途なら小さい n に限定する |
| ブロードキャスト対象が大きい | Driver と全 Executor のメモリを消費する | 小さいテーブルに限定する |

```python
# NG: Driver に全件を集めてループ
for row in df.collect():
    if row["status"] == "active":
        results.append(transform(row))

# OK: 分散したまま列単位に変換
from pyspark.sql import functions as F
result = df.filter(F.col("status") == "active").withColumn("x", F.upper("name"))
```

例外: 設定値や件数の少ないマスタなど、**上限件数が明らかに小さい**データの `collect()` は問題ない。その場合も、なぜ小さいと言えるのかが分かるようにコメントで残させる。

## 2. 分散処理を活かせていない書き方

- **Python UDF（`@udf`、`F.udf`）**: 行ごとに JVM と Python の間でデータをやり取りするため遅い。まず `pyspark.sql.functions` の組み込み関数で書けないかを確認する。これが第一の選択肢
- **`pandas_udf` / `mapInPandas` / `applyInPandas`**: Arrow でまとめて渡すので通常の UDF より速いことが多いが、Python での実行とデータ変換のコストは残る。また、バッチやグループ単位で Executor のメモリに載るため、グループが大きい（`applyInPandas` で特定キーに件数が偏るなど）と Executor が OOM になる。「使えば速い」とは書かず、組み込み関数で表現できないときの選択肢とし、実データ量での計測を勧める
- **`rdd.map` / `rdd.foreach` などの RDD API**: Catalyst による最適化が効かない。DataFrame API で書けないかを確認する
- **Executor 内での boto3 呼び出し**: `foreach` や UDF の中で 1 行ずつ S3 / DynamoDB API を呼ぶと、スロットリングやコネクション枯渇が起きる。`foreachPartition` でパーティション単位にクライアントを作りバッチ送信するか、Glue のコネクタ・`write_dynamic_frame` で書き込めないかを確認する
- **Executor からの外部への書き込みと再実行**: Spark はタスクの失敗時に同じタスクを再試行する。Executor の喪失による再計算や、投機的実行（遅いタスクの複製実行）が有効な場合もあり、**同じパーティションの処理が複数回実行されうる**。そのため、`foreach` / `foreachPartition` / UDF の中で外部サービスへ書き込む処理（API 呼び出し、DB 更新、メッセージ送信など）は、同じ書き込みが 2 回以上起きても安全かを確認する。バッチ化しても、この問題は解決しない
  - 冪等にする手段の例: 冪等キーによる重複の防止、条件付き書き込み（DynamoDB の条件式など）、UPSERT、下流での重複排除
  - UDF の中に副作用を持たせない。UDF は最適化や再計算によって、想定と異なる回数だけ実行されることがある
  - ジョブ全体のリトライ・再実行（9.）でも同じ書き込みが繰り返される点もあわせて確認する
- **Driver 側での Python ループによる DataFrame 生成**: 日付ごとに `for` で読み込み → `union` を繰り返すと DAG が肥大化する。パスのリストやパーティション条件でまとめて 1 回で読む

## 3. 読み込み時のパーティション（プルーニング）

プルーニング = 条件に合わないパーティションを最初から読まないこと。読み込み量に直結するため、データが毎日増えるテーブルでは運用期間に比例してコストが膨らむ。

`create_dynamic_frame.from_catalog` で読む場合、パーティションを絞るのは読み込み時のオプションの役割。条件なしで読んで `toDF()` 後に `filter` しても、Spark のパーティションプルーニングには頼れず、全パーティションを列挙・読み込む可能性が高い。

```python
# 要確認: 読み込み時に条件がない
dyf = glueContext.create_dynamic_frame.from_catalog(database="db", table_name="events")
df = dyf.toDF().filter("dt = '2026-10-01'")

# 推奨: 読む前にパーティションを絞る
dyf = glueContext.create_dynamic_frame.from_catalog(
    database="db",
    table_name="events",
    push_down_predicate="dt = '2026-10-01'",
    # パーティション数が非常に多いテーブルで、Partition Index がある場合はこちらも有効
    additional_options={"catalogPartitionPredicate": "dt = '2026-10-01'"},
    transformation_ctx="events_src",
)
```

- `push_down_predicate` は**パーティション列だけ**に効く。パーティション列でない条件を書いても、読み込むデータは減らない
- `spark.read` や Spark SQL でカタログテーブルを読む場合は、パーティション列への `filter` で Spark 側のプルーニングが効くことが多い。この場合は `filter` があるだけで「全件読んでいる」と断定しない
- 実際に何を読んでいるかの確認方法は、読み方によって異なる。断定できないときは確認方法を添えて指摘する
  - **`spark.read` / Spark SQL で読む場合**: `df.explain()` の FileScan に出る `PartitionFilters` が、**パーティションの絞り込み**の指標。`PushedFilters` は、Parquet などのデータソースに押し込まれたフィルター（ファイル内の行グループの読み飛ばしなど）を示すもので、**パーティションが絞られたことの根拠にはならない**。2 つを混同しない
  - **DynamicFrame（`from_catalog`）で読む場合**: `push_down_predicate` は、カタログからパーティション一覧を取得した後、S3 のファイル一覧を取得する前に Glue が適用するもので、Spark の FileScan の指標とは仕組みが別である。`explain()` の表示だけで効いている・いないを判断せず、Spark UI の入力サイズや読み込んだファイル数で確認する
- **小さいファイルの大群**: 入力が小さいファイルの大群だと、タスク数が爆発する。`groupFiles: "inPartition"` と `groupSize` でファイルをまとめて読める（テーブルのプロパティ、または `from_options` の接続オプションで指定する）。ただし、**対応する形式は CSV / JSON / XML など**で、**Parquet / ORC / Avro には効かない**。また、入力ファイルが 50,000 を超えると自動で有効になる。形式を確認せずに一律に勧めない

## 4. 書き込み時のパーティションとファイル数

- **パーティション列の指定**: 後続でよく絞り込まれる列（日付など）を `partitionKeys` に指定しているか。逆に、カーディナリティが高い列（ユーザー ID など）をパーティション列にして、パーティションが大量にできていないか
- **ファイル数・サイズ**: Spark のタスク数に応じてファイルが出力される。小さいファイルが大量にできると、後続の読み込みと S3 のリスト取得が遅くなる。逆に巨大な 1 ファイルは後続の並列読み込みを妨げる
- **調整方法は一律に決めない**: 適切なファイル数はデータ量・出力先・下流の読み方で変わる。処方箋を 1 つに決め打ちせず、出力データ量の見込みから考えさせる
  - `coalesce(n)`: シャッフル（Executor 間のデータ再配置）なしで減らせるが、上流の処理の並列度まで下がることがある
  - `repartition(n)`: シャッフルが発生し、データを n 個に分散し直す。偏りが緩和されることはあるが、行サイズの違いなどにより、各タスクの処理量やファイルサイズが均等になるとは限らない
  - `repartition("dt")` のように列だけ指定すると、**同じ値の行は 1 タスクに集まる**。対象日が 1 日分なら、シャッフル後の処理と書き出しが 1 タスクに集中する（下記の `repartition(1)` と同じ状態）。パーティションごとのファイルサイズも保証されない
  - Spark の `maxRecordsPerFile` オプションで 1 ファイルの行数上限を設ける方法もある
- **`coalesce(1)` / `repartition(1)`**: どちらも最終的に 1 タスクで全データを書き出すため、大きいデータでは問題になりうる。ただし、**並列度が失われる範囲が異なる**ので区別して指摘する
  - `coalesce(1)`: シャッフルなしでパーティションをまとめるため、**上流の処理（読み込み・変換）まで 1 タスクに巻き込まれる**ことがある。重い変換の後に `coalesce(1)` があると、その変換全体が並列に実行されなくなる
  - `repartition(1)`: シャッフルが入るため、**上流の処理は並列に実行できる**が、シャッフル後の処理と書き出しが 1 タスクに集中する。全データを一度にメモリに保持するわけではないが、その 1 タスクの処理時間、シャッフルの読み込み量、メモリやローカルディスク（溢れたデータの退避先）の使用量がボトルネックになりうる
  - どうしても 1 ファイルが必要な場合、上流が重いなら `coalesce(1)` より `repartition(1)` の方がよいことが多い。ただし、そもそも 1 ファイルである必要があるか（下流の要件）を先に確認させる。大きいデータで 1 ファイル出力が必要ないなら High として指摘する
- **形式**: 分析用途の出力は Parquet などの列指向形式にする。CSV / JSON 出力には理由があるかを確認する
- **カタログへの反映**: 新しいパーティションを書いても Data Catalog に登録されなければ Athena などから見えない。クローラーや `enableUpdateCatalog`、`MSCK REPAIR` / パーティション追加など、反映方法が決まっているか

## 5. 再計算とキャッシュ

Action（`count()`、`write`、`collect()` など、実際の計算を起こす呼び出し）を呼ぶたびに実行が起きる。キャッシュなどがなければ、同じ上流処理（読み込みや Join）が Action ごとに再実行されることがある。どこまで再実行されるかは処理計画・Action・入力形式による（Spark がシャッフル結果を再利用してステージを省略することもある）。

- 同じ大きい DataFrame に対して複数の Action があるなら、`cache()` / `persist()` で再計算を避けられないかを確認する。使い終わったら `unpersist()` する
- **ログ用の `count()`**: 「件数をログに出す」だけのために大きい DataFrame で `count()` すると、その分の実行が増える。必要性を確認する
- 逆に、1 回しか使わない DataFrame への `cache()` はメモリの無駄になる。Executor メモリに収まらない量の `cache()` はディスクへの退避や再計算を招く

## 6. Join とデータの偏り（スキュー）

- 片方が小さいテーブルなら `F.broadcast(small_df)` でシャッフルを避けられる
- Join キーに NULL や特定の値が集中していると、1 タスクだけが極端に遅くなる / OOM になる。キーの分布を考慮しているか（NULL を事前に除外する、salting など）
- AQE（実行時に統計を見て Join 方式やパーティション数を調整する機能）はスキューや小さいテーブルの Join をある程度自動で緩和する。ただし Glue バージョンとジョブの実効設定（`spark.sql.adaptive.*`）で有効かどうかが決まるので、「AQE があるから大丈夫」と決めつけず確認する。明らかな偏りはコードで対処すべき
- 直積（`crossJoin`、Join 条件の書き忘れ）がないか
- Join の結果、片方のキー重複で行数が膨らんでいないか（マスタ側のキーが一意である前提が崩れると、金額などが二重計上される）

## 7. DynamicFrame と DataFrame

- `toDF()` / `DynamicFrame.fromDF()` の往復が多くないか。DataFrame で処理するならまとめて変換し、入出力の境界でだけ DynamicFrame を使う
- スキーマが揺れる入力（同じ列に文字列と数値が混在するなど）では `resolveChoice` で型を明示しているか。`choice` 型のまま `toDF()` すると予期しない struct 型になる
- `ApplyMapping` で列名・型を明示しているか。暗黙の型推論に頼っていないか
- `spark.read` で `inferSchema=True` を大きい CSV に使うと、推論のために余分にデータを読み込む。スキーマを明示する

## 8. ジョブブックマーク

ブックマーク = 前回までに処理した**入力（ソース）**を記録し、次回は新しい分だけを読む機能。

押さえるべき仕組み:

- **ジョブ定義でブックマークが有効になっていること**（`--job-bookmark-option job-bookmark-enable`）と、**ブックマーク対応のソースを `transformation_ctx` 付きで読んでいること**の両方がそろって初めて機能する。既定は無効。以下の確認項目は、この前提が満たされている（または満たされうる）場合に当てはまる。ジョブ定義が見えなければ、有効・無効のどちらの前提で評価したかを明記する
- 状態は `job.init(...)` で読み込まれ、**`job.commit()` を呼んだときに保存される**
- 追跡されるのは**ソースだけ**。出力先（シンク）は追跡されず、ブックマークで出力の重複が防がれるわけではない。リセットや巻き戻しをしても、出力済みのファイルは削除されない
- 状態はソースごとの `transformation_ctx` をキーに保存される
- 対象は JDBC ソースと一部の S3 ソース（JSON / CSV / Avro / XML / Parquet / ORC など）。`spark.read` で直接読む部分は対象外

確認すること:

- **`job.commit()` がない**: ブックマークが更新されないので、**毎回同じ入力を再処理する**（差分処理になっていない）。出力が追記なら、結果として出力が重複する。影響の大きさは出力の書き方次第なので、出力側と合わせて重要度を判断する
- **失敗したのに `job.commit()` される**: 例外を握りつぶしてから `commit()` すると、処理できなかった入力が「処理済み」になり、**次回以降も読まれず欠損する**。こちらの方が気づきにくく危険
- **ソースの `transformation_ctx` が一意で、実行をまたいで安定しているか**: 実行ごとに変わる値（日時など）を入れると、毎回別のソースとして扱われ、差分読みにならない
- **入力元の変更**: `transformation_ctx` を変えずに入力パスなどを変えると、古い状態が新しい入力に適用され、期待どおりに動かない可能性がある（AWS のベストプラクティスでは、新しいパスのファイルが読み飛ばされうると警告している）。入力元を変える変更では、挙動の確認と、ブックマークのリセットや `transformation_ctx` の変更が必要かを検討させる
- **ブックマーク対象のソースを意図せず差分読みにしていないか**: ブックマークが有効なジョブで、マスタのように毎回全件読むべきソースに `transformation_ctx` を付けると、2 回目以降は新しいファイルがなく空になる可能性がある
- **新着データがない実行**: 入力が空になったときに後続処理（Join、書き込み）が失敗しないか
- ブックマークの仕組みは「どこまで読んだか」の管理であって、出力の整合性は 9. で別途確認する

## 9. 失敗・再実行時の出力の整合性（冪等性）

Glue ジョブはリトライ・手動再実行・同時実行がありうる。冪等性 = 同じ入力で何度実行しても結果が同じになること。ブックマークとは別問題として、出力の書き方ごとに「途中で失敗したら」「2 回実行したら」「2 つ同時に動いたら」を確認する。

- **追記（`append`）**: 再実行やリトライで重複する。書き込み後・`commit()` 前に落ちた場合も、次回同じ入力を再処理して重複する。下流での重複排除、または上書き方式への変更を検討する
- **全体上書き（`overwrite`、静的モード）**: 出力先の既存データを全部消す。差分処理と組み合わせると過去分が消える
- **パーティション単位の上書き（`partitionOverwriteMode=dynamic` + `overwrite`）**: 書き込んだパーティションだけを置き換える。**そのパーティションの全データを毎回書く処理（日次の全量再作成など）では有効**だが、差分処理（毎時の追記分だけを書くなど）では、そのパーティションの過去分が最新の差分で置き換わって消える
- **削除してから書く**（`purge_s3_path` など）: 削除後・書き込み前に失敗すると、データが消えたままになる
- **テーブル形式（Iceberg / Hudi / Delta）**: トランザクションや `MERGE` で、失敗・再実行・同時実行に強い出力にできる。要件が厳しいなら選択肢として挙げる
- **同時実行**: 同じ出力先に書くジョブが重なると壊れうる。ジョブ定義の同時実行数（`MaxConcurrentRuns`）を確認する

## 10. データ品質とスキーマ

- **不正・破損レコード**: パースできない行、必須列の NULL、想定外の値をどう扱うか（落とす / 隔離して別出力 / ジョブを失敗させる）。黙って落としていないか、件数が分かるか
- **inner join で行が消える**: マスタに存在しないキーの行が黙って消えていないか。意図した挙動か
- **スキーマ変更**: 上流で列追加・型変更が起きたときに、ジョブが失敗するのか、黙って NULL になるのか
- **型変換・精度**: 金額を `double` で扱っていないか（`decimal` を検討）。文字列から数値・日付への変換失敗が NULL になって気づけない、ということがないか
- **タイムゾーン**: 日付パーティションや「前日分」の計算が UTC と JST のどちらの基準か明確か
- **遅延到着データ**: 対象日を過ぎてから届くデータをどう扱うか（再処理するのか、捨てるのか）

## 11. 設定・パラメータ・ログ

この章の項目は、書き方の形式だけで機械的に指摘しない。**運用上の影響がある場合**（環境ごとに値を変えられずデプロイ事故になる、障害時に原因を追えない など）は指摘し、影響がなく好みの範囲なら 💡Suggestion にとどめる。

- **ハードコード**: S3 パス、DB 名、日付など、環境（開発 / 本番）や実行ごとに変わる値がハードコードされていないか。実行ごとに変わらない定数まで外出しを求めない。ジョブパラメータは `getResolvedOptions(sys.argv, [...])` で受け取れる
- 任意のパラメータを `getResolvedOptions` で必須として扱い、未指定時にジョブが落ちないか
- **ログの内容**: 処理対象（入力パス・対象日など）、処理件数、失敗件数と失敗理由など、**障害時に後から調査できる情報が残っているか**を確認する。不足していれば指摘する。Driver での `print` も標準出力として CloudWatch Logs に残りうるため、`print` を使っていること自体は問題にしない。ログレベルで出し分けたい場合などに `glueContext.get_logger()` や `logging` を 💡Suggestion として提案する
- **Executor 側のログ**: UDF や `foreachPartition` の中で出したログ（`print` を含む）は Executor のログに出力され、Driver のログには出ない。障害調査でそのログを当てにしている場合は、どこに出るかを確認させる
- 例外を握りつぶしてジョブが「成功」扱いになっていないか

## 12. 運用・コスト

コードだけでは判断できないことが多い。ジョブ定義（IaC など）があれば合わせて確認し、なければ確認事項として挙げる。

- **ワーカータイプ / ワーカー数（DPU）**: データ量に対して過大・過小でないか
- **タイムアウト・リトライ・同時実行数**: 既定値任せになっていないか。リトライするなら 9. の冪等性が前提になる
- **OOM の対処**: DPU やワーカーサイズを増やせば解決するとは限らない。Driver 集約（1.）、偏り（6.）、巨大なパーティションやグループ（2.・4.）など根本原因を先に疑う
- **シャッフルによるディスク逼迫**: 大きいシャッフルでメモリから溢れたデータがローカルディスクに書かれ（spill）、ディスクが尽きて失敗することがある。シャッフル量を減らす、パーティション数を調整するなどを検討する
- **調査手段**: 遅い・落ちる原因の調査には Glue の Spark UI（どのステージ・タスクが遅いか、spill やスキューの有無）と CloudWatch のジョブメトリクスを使うよう勧める。Glue コンソールの Spark UI は Glue 3.0 以降で使えるが、ジョブ設定で Spark UI（イベントログの S3 への保存）を有効にしておく必要がある。無効のままだと、問題が起きた実行を後から調べられない

## 13. セキュリティと接続

- 認証情報のハードコードがないか。AWS リソースへのアクセスはジョブの IAM ロールで行い、DB のパスワードなどは Secrets Manager や Glue Connection から取得する
- IAM ロールの権限が、ジョブが行う操作とリソースに対して最小限か。`*` やバケット全体への権限があるだけで過剰権限と判定しない（AWS の操作には、リソースを個別に指定できず `*` が必要なものもある）。必要な操作・リソースより明らかに広い権限（使わない操作の許可、無関係なバケットへの書き込み など）を指摘し、`*` を使っている場合は、その理由が説明できるかを確認する
- 出力先や一時ディレクトリの暗号化（KMS、Glue のセキュリティ設定）が要件どおりか
- VPC 内のリソース（RDS など）に接続する場合、Glue Connection、サブネット、セキュリティグループ、ルートの構成が前提として整理されているか。S3 などの AWS サービスへ閉域で接続する要件がある場合は、VPC エンドポイントの有無も確認する（常に必要なわけではない）
- Lake Formation で権限管理しているテーブルを読む場合、その権限モデルに沿ったアクセス方法か（Glue バージョンによって対応方式が異なる）
- ログに個人情報や機密値を出力していないか
