# バックエンドレビューガイドライン

[バックエンド設計ガイドライン](./backend-design.md)をもとにバックエンドコードレビューをする際の観点をレイヤーごとにまとめてチートシートになります。

## 共通(全レイヤー)

以下の項目は重要度**🚨High**

- レイヤーの参照方向
  - 許可されていない方向へのimportが無いか(domainがadapterに依存しているなど)
- タイムゾーン
  - 内部処理ではUTCを用いて、ユーザー見えする出力などでは設定したTZを使用しているか
- 機密情報の取り扱い
  - パスワード、トークン、APIキーなどをログや例外メッセージに出力していないか
  - シークレットがハードコードされていないか(環境変数やシークレットマネージャ経由になっているか)

以下の項目は重要度**⚠️Middle**

- 命名規則
  - ファイル名は命名規則通り{役割}_{コンポーネント種別}.py, {役割}.{コンポーネント種別}.tsになっているか
  - クラス名はアッパーキャメルに統一されているか
  - パラメータや変数名がlowerCamelCaseになっているか
- 例外処理
  - 業務例外の400(BusinessError)とアプリ例外の500(ApplicationError)が正しく使い分けできているか
  - 例外処理はGlobalExceptionに集約されているか
- 冗長コード
  - 不要な型アサーションが混在していないか
  - 早期リターンを行っているか
- ロギング
  - ログレベル(DEBUG/INFO/WARN/ERROR)が用途に応じて使い分けられているか
  - リクエストIDや相関IDが出力され、後から追跡可能な構造になっているか
- 型付け
  - 関数シグネチャに型ヒント(Python)/型注釈(TS)が付与されているか
  - `Any`型や`unknown`型を安易に使っていないか
- 非同期処理
  - `async def`関数の中で同期I/O(ブロッキングDB呼び出し、`requests`など)を呼んでいないか
  - `await`忘れが無いか

以下の項目は重要度**ℹ️Low**

- 適切なコメント
  - 後で見返したり別の作業者がすぐに理解できるように適切なコメントを残すこと
- デッドコード
  - いつか使うかもしれないと使わなくなった処理をコメントアウトで残さない
  - 呼び出しの無くなった関数などは削除すること
- TODO/FIXME
  - 未対応のTODO/FIXMEコメントを放置していないか(チケット化などで追跡可能になっているか)
- テスト整合性
  - 実装変更に対応するテストが追加/更新されているか

## Viewレイヤー(BFF)

以下の項目は重要度**🚨High**

- 画面仕様の閉じ込め
  - 画面専用のロジックはViewレイヤーの中のみで外部に漏れ出てはいけない
- URLパス形式
  - 画面専用のことがわかるようにAPIのパスは`/**/view/**`という構成になっているか
- 他画面との非共有
  - 複数画面で共有することなく、1画面１ViewControllerとする
- レイヤーの参照方向
  - Viewからの参照はApplicationかDomainのみであるか
- 認証・認可
  - エンドポイントに認証依存(Depends)が付与されているか
  - 画面が表示するリソースに対するアクセス権(ロールや所有権)が検証されているか

以下の項目は重要度**⚠️Middle**

- リクエスト入力検証
  - リクエストはクライアントとアプリとの契約内容であり、アプリ事情が入りこまないスキーマになっていること
  - リクエストに対して、型や桁数、必須かどうかのチェックを行っているか
- リクエスト変換
  - ユースケースにリクエスト内容を渡す際にはMapperなどの変換機構を通してDTOに適切に変換すること
- レスポンス変換
  - DTOからクライアントとの契約内容であるスキーマにMapperなどの変換機構を通して適切に変換すること
- HTTPメソッド・ステータス
  - REST規約に沿ったHTTPメソッド/ステータスコードになっているか
- 楽観ロック
  - 更新系APIにversionヘッダーが定義されているか
  - 削除系APIにversionヘッダーが定義されているか
- 責任原則
  - WebAPIとしてHTTPリクエストを受け取り内部のビジネスロジックであるApplication層に処理を委譲すること
  - Application層の処理やMapperなどの外部コンポーネントの責務を抱え込んでいないか
- N+1問題
  - 複数リソースを結合するBFFで、Repository呼び出しをループ内で繰り返すなどN+1を誘発する構造になっていないか
- レスポンス機密情報
  - パスワードハッシュ、内部専用ID、監査カラムなど画面に不要な情報が漏れていないか

## Adapterレイヤー

### Controller

以下の項目は重要度**🚨High**

- レイヤーの参照方向
  - adapterからapplication、adapterからdomainへの参照のみになっているか
- URLパス形式
  - ケバブケースになっているか
  - 設計書の`/{resource-name}/{ids}`形式に沿った集約ルート単位の構成になっているか
- ヘッダー
  - リクエストのヘッダーオブジェクトは文字列情報のためversionなどはNumer型で扱う場合はキャストする必要がある
- 認証・認可
  - エンドポイントに認証依存(Depends)が付与されているか
  - 対象リソースに対する認可(オーナー検証、ロール検証)が行われているか

以下の項目は重要度**⚠️Middle**

- リクエスト入力検証
  - リクエストはクライアントとアプリとの契約内容であり、アプリ事情が入りこまないスキーマになっていること
  - リクエストに対して、型や桁数、必須かどうかのチェックを行っているか
- リクエスト変換
  - ユースケースにリクエスト内容を渡す際にはMapperなどの変換機構を通してDTOに適切に変換すること
- レスポンス変換
  - DTOからクライアントとの契約内容であるスキーマにMapperなどの変換機構を通して適切に変換すること
- HTTPメソッド・ステータス
  - REST規約に沿ったHTTPメソッド/ステータスコードになっているか
- 楽観ロック
  - 更新系APIにversionヘッダーが定義されているか
  - 削除系APIにversionヘッダーが定義されているか
- 責任原則
  - WebAPIとしてHTTPリクエストを受け取り内部のビジネスロジックであるApplication層に処理を委譲すること
  - Application層の処理やMapperなどの外部コンポーネントの責務を抱え込んでいないか
- URLバージョニング
  - 将来の破壊的変更に備えて`/v1/`などのバージョニング方針に沿ったパスになっているか

### Infrastructure

以下の項目は重要度**🚨High**

- DB依存機能の禁止
  - DB固有の関数や構文の利用は使用してはいけない
- テーブル命名
  - テーブル名はスネークケースで定義すること
- トランザクション境界
  - Session/UnitOfWorkのライフサイクルが1リクエスト = 1トランザクションで管理されているか
  - Repository実装内で勝手にcommit/rollbackを行っていないか(トランザクション制御は上位に任せているか)

以下の項目は重要度**⚠️Middle**

- クエリ安全性
  - パラメータバインディングを使っているか
- 件数上限の判定
  - 件数上限を設けている場合、超過判定を全件取得前に行っているか
- ソート安定
  - ページングと組み合わせるクエリにはORDER BYが付いているか
- バリデーション
  - sqlalchemyやclass-validatorを用いて桁数や型、必須項目チェックを行っているか
- エンティティの不変性
  - エンティティクラスのメソッドを通してフィールドを変更しているか
- N+1問題
  - 関連エンティティ取得で`joinedload`/`selectinload`など eager loading が必要な箇所を見落としていないか
  - コレクションに対するループ内でRepositoryを呼び出していないか
- インデックス活用
  - WHERE / JOIN / ORDER BY のキーが既存インデックスと整合しているか
  - 検索頻度の高い新規カラム追加時にインデックス設計が検討されているか
- マイグレーション
  - スキーマ変更に対応するAlembicマイグレーションが同PRに含まれているか
  - NOT NULLカラム追加時のデフォルト値、リネーム時の後方互換など、本番適用時のリスクが考慮されているか
- ドメインモデル境界
  - Repository実装がSQLAlchemyモデル(ORMエンティティ)を外部に漏らさず、ドメインモデルに詰め替えて返しているか

### Mapper / Command / Converter

以下の項目は重要度**⚠️Middle**

- 境界マッピング
  - プレゼンテーションモデルからアプリケーションDTOまたはその逆は変換機構を通しているか
  - アプリケーションDTOからドメインモデルまたはその逆は変換機構を通しているか
- nullable変換
  - undefinedとnullを適切にデフォルト値や省略フィールドとして扱っているか
- 一括コピー
  - シャローコピーやディープコピーなどを用いて変換処理を行っていないか
- 型
  - any型や安易な型アサーションを使っていないか

以下の項目は重要度**ℹ️Low**

- 単方向依存
  - Mapperがドメイン/DTOに依存する向きが逆転していないか(ドメインからMapperを参照していないか)

## Applicationレイヤー

### Usecase

以下の項目は重要度**🚨High**

- ドメインロジックの染み出し
  - 分岐・繰り返し・業務ルールが記述されていないか
- レイヤーの参照方向
  - 許可されていない方向へのimportが無いか(adapterを参照していないか)
- 認可の実施
  - ユースケース入り口で「その操作を実行可能な主体か」の認可判定が行われているか(Controller層のみに依存していないか)

以下の項目は重要度**⚠️Middle**

- トランザクション管理
  - トランザクションはUoWに一任しているか
  - ユースケース実装にロールバックなどの処理を記述していないか
- 戻り値
  - MapperやConveterなどの変換機構を通して、ドメインモデルからアプリケーションDTOに変換して返しているか
- 副作用の順序
  - 外部API呼び出しとDB更新の順序が失敗時の不整合を招かない設計になっているか(必要ならアウトボックス等の仕組みを検討しているか)
- 冪等性
  - 決済・通知など二重実行が致命的な処理で、冪等キーやユニーク制約による保護がされているか

以下の項目は重要度**ℹ️Low**

- ユースケースの粒度
  - 1ユースケース = 1つの業務目的になっているか(複数の目的が混在していないか)

## Domainレイヤー

以下の項目は重要度**🚨High**

- 業務仕様の閉じ込め
  - ビジネスルール(計算・判定・状態遷移)がエンティティやドメインサービスに閉じ込められているか
- レイヤーの参照方向
  - 許可されていない方向へのimportが無いか(adapter/infrastructure/applicationに依存していないか)
- Repositoryのインターフェイス
  - データアクセスのインターフェースがドメイン層に定義されているか
  - 引数や戻り値にドメインモデルが使われているか。インフラ層のデータモデルの汚染が無いか
- 完全カプセル化
  - 直接ドメインモデルを書き換えることはせず、必ずドメインメソッドを経由すること
- 不変条件
  - ファクトリメソッドや更新メソッドの内部で、ドメインモデル単体で完結する整合性チェックを漏れなく実装しているか
- フレームワーク非依存
  - `fastapi` / `sqlalchemy` / `pydantic` などフレームワーク・インフラのimportがドメイン層に混入していないか

以下の項目は重要度**⚠️Middle**

- 新規作成の隠蔽
  - UseCase層などでインフラ都合の初期値を意識しないようにファクトリメソッドで生成ロジックが隠蔽されているか
- ステートレスの維持
  - ドメインサービス自体が内部状態(フィールド変数)を持たず、計算機や測定機として完全にステートレスな設計になっているか
- 命名規則
  - ドメインの関心事に沿ったコレクションとしての命名になっているか
- 値オブジェクト
  - Email, Money, IDなど意味のあるプリミティブが値オブジェクトとして定義され、単なるstr/intでばらまかれていないか
- 集約境界
  - 1つの集約ルート経由でしか子エンティティを更新できない設計になっているか(子エンティティを直接触っていないか)

以下の項目は重要度**ℹ️Low**

- ユビキタス言語
  - ドメイン用語がチーム内の仕様書や共通言語と一致しているか(訳語や省略形のブレがないか)
