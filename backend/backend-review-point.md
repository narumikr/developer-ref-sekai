# バックエンドレビューガイドライン

[バックエンド設計ガイドライン](./backend-design.md)をもとにバックエンドコードレビューをする際の観点をレイヤーごとにまとめてチートシートになります。

## 共通(全レイヤー)

以下の項目は重要度**🚨High**

- レイヤーの参照方向
  - 許可されていない方向へのimportが無いか(domainがadapterに依存しているなど)
- タイムゾーン
  - 内部処理ではUTCを用いて、ユーザー見えする出力などでは設定したTZを使用しているか

以下の項目は重要度**⚠️Middle**

- 命名規則
  - ファイル名は命名規則通り{役割}_{コンポーネント種別}.py, {役割}.{コンポーネント種別}.tsになっているか
  - クラス名はアッパーキャメルに統一されているか
  - パラメータや変数名がlowerCamelCaseになっているか
- 例外処理
  - 業務例外の400(BusinessError)とアプリ例外の500(ApplicationError)が正しく使い分けできているか
  - 例外処理はGlobalExceptionに集約されているか
- 冗長コード
  - 不要な型アサーションが混在していないか
  - 早期リターンを行っているか

以下の項目は重要度**ℹ️Low**

- 適切なコメント
  - 後で見返したり別の作業者がすぐに理解できるように適切なコメントを残すこと
- デッドコード
  - いつか使うかもしれないと使わなくなった処理をコメントアウトで残さない
  - 呼び出しの無くなった関数などは削除すること

## viewレイヤー(BFF)

以下の項目は重要度**🚨High**

- 画面仕様の閉じ込め
  - 画面専用のロジックはViewレイヤーの中のみで外部に漏れ出てはいけない
- URLパス形式
  - 画面専用のことがわかるようにAPIのパスは`/**/view/**`という構成になっているか
- 他画面との非共有
  - 複数画面で共有することなく、1画面１ViewControllerとする
- レイヤーの参照方向
  - Viewからの参照はApplicationかDomainのみであるか

以下の項目は重要度**⚠️Middle**

- リクエスト入力検証
  - リクエストはクライアントとアプリとの契約内容であり、アプリ事情が入りこまないスキーマになっていること
  - リクエストに対して、型や桁数、必須かどうかのチェックを行っているか
- リクエスト変換
  - ユースケースにリクエスト内容を渡す際にはMapperなどの変換機構を通してDTOに適切に変換すること
- レスポンス変換
  - DTOからクライアントとの契約内容であるスキーマにMapperなどの変換機構を通して適切に変換すること
- HTTPメソッド・ステータス
  - REST規約に沿ったHTTPメソッド/ステータスコードになっているか
- 楽観ロック
  - 更新系APIにversionヘッダーが定義されているか
  - 削除系APIにversionヘッダーが定義されているか
- 責任原則
  - WebAPIとしてHTTPリクエストを受け取り内部のビジネスロジックであるApplication層に処理を委譲すること
  - Application層の処理やMapperなどの外部コンポーネントの責務を抱え込んでいないか

## adapterレイヤー

### Controller

以下の項目は重要度**🚨High**

- レイヤーの参照方向
  - adapterからapplication、adapterからdomainへの参照のみになっているか
- URLパス形式
  - ケバブケースになっているか
- ヘッダー
  - リクエストのヘッダーオブジェクトは文字列情報のためversionなどはNumer型で扱う場合はキャストする必要がある

以下の項目は重要度**⚠️Middle**

### RepositoryImpl

以下の項目は重要度**🚨High**

- DB依存機能の禁止
  - DB固有の関数や構文の利用は使用してはいけない
- テーブル命名
  - テーブル名はスネークケースで定義すること

以下の項目は重要度**⚠️Middle**

- クエリ安全性
  - パラメータバインディングを使っているか
- 件数上限の判定
  - 件数上限を設けている場合、超過判定を全件取得前に行っているか
- ソート安定
  - ページングと組み合わせるクエリにはORDER BYが付いているか
