# AWS Glue Spark ジョブ コードレビュー

Glue の Spark ジョブの Python コードは「1台のマシンで動く Python」として書くと、正しく動いても遅い・高い・OOM で落ちる、という壊れ方をする。
このレビューの目的は、**Spark の分散処理とブックマークなどの Glue の機能を正しく使えているか**を確認し、そうなっていない箇所を是正することにある。
文法やスタイルの指摘は二の次でよい。データ量が 100 倍になったとき、または失敗・再実行が起きたときに壊れる箇所を優先して見つける。

Spark の挙動は処理計画・入力形式・設定で変わる。コードを読むだけでは確定できないこと（実際に読むパーティション、再計算の有無、AQE の効き方など）は断定せず、「〜の可能性がある。`explain()` や Spark UI で確認を」のように確認方法を添えて書く。断定した誤検出は、レビュー全体の信頼を落とす。

## レビュー手順

### 1. ジョブの前提を把握する

コードと周辺ファイル（IaC、ジョブ定義、README など）から以下を特定する。不明なものは推測した前提としてレビュー冒頭に明記する。

- **ジョブタイプと実装の食い違い**: ジョブ定義のコマンド名（Spark ETL ジョブは `glueetl`、Python Shell ジョブは `pythonshell`）とコードの両方を見て、次のように判断する
  - **ジョブ定義が Python Shell なのに、コードに Spark の実装がある**: 🚨High として指摘する。Python Shell の環境には Spark がないため、import やコンテキスト生成の時点でジョブが失敗する可能性が高い。ジョブ定義とコードのどちらが意図どおりかを確認させる。この指摘を書いたら、Spark としての詳細なレビューには進まない（前提となる実行環境が決まっていないため）
  - **コードに Spark の実装がなく、pandas / boto3 などの通常の Python だけで書かれている**: Python Shell ジョブのコードである可能性が高い。このスキルの対象外であることを伝えてレビューを終える
- **Glue バージョンと実効設定**: ジョブ定義の Glue バージョン、ワーカータイプ / DPU、`--conf` などで渡している Spark 設定。バージョンごとに Spark / Python のバージョンや使える機能が異なるので、特定のバージョンを前提にせず実際の定義を確認する。AQE などは「そのバージョンで使える」ことと「このジョブで有効になっている」ことを区別する
- **入出力**: Data Catalog 経由か S3 直接か、ファイル形式、パーティション列
- **想定データ量**: 分からなければ「本番で数百 GB 規模になりうる」と仮定して評価する

### 2. 処理の流れを Driver / Executor の視点で追う

上から順に、各処理が **Driver で動くのか Executor で分散されるのか**、**どこで Action（実計算）が発生するか**を意識して読む。
Spark は遅延評価なので、Action を呼ぶたびに実行が起きる。キャッシュなどがなければ、同じ上流処理（読み込みや Join）が Action ごとに再実行されることがある。どこまで再実行されるかは処理計画・Action の種類・入力形式による（例: `show()` は必要な行数分だけ評価して済む場合がある）。

### 3. チェックリストで確認する

`references/pyshell-checklist.md` を読み、該当する観点を確認する。チェックリストは網羅を目指したものではなく、よくある失敗パターン集である。
リストにない問題でも「Driver にデータが集まる」「同じ計算が繰り返される」「読む/書くデータ量が必要以上に多い」「失敗・再実行で出力が壊れる」に当てはまるなら指摘する。

### 4. 指摘を書く

各指摘は以下のテンプレートで書く。改善後のコード例は、コードから前提が読み取れて安全に示せる場合に添える。ジョブ設定・インフラ・要件など、コードの外の情報に依存する指摘では、推測で書いたコードはそのまま貼られて事故の元になるので、コード例の代わりに「確認すべきこと」と「改善の方針」を書く。Glue 特有の問題はなぜダメなのかが直感的でないため、「何が起きるか（例: 全件が Driver に転送され OOM）」を具体的に説明すること。
レビューを読むのは Glue / Spark に不慣れな開発者である可能性が高い。「遅延評価」「シャッフル」「プルーニング」などの用語は初出で一言説明を添え、指摘が次に同じコードを書くときの学びになるようにする。

````md
## <!-- 指摘内容の要約 -->

- **重要度**: [ 🚨High / ⚠️Medium / ℹ️Low / 💡Suggestion ]
- **箇所**: `path/to/job.py:42`
- **観点**: <!-- 例: Driver 集約 / パーティション / ブックマーク -->

**詳細**

<!-- 何が問題で、データ量が増えたとき・本番で何が起きるか -->

**改善案**

```python
# 修正後のコード（安全に示せる場合）
```

<!-- コード例を示せない場合は、確認事項と改善方針を書く -->

**補足**

<!-- トレードオフ、前提条件、同様の箇所が他にあればそのパス -->
````

重要度の目安:

- **🚨High**: データ量増加で OOM / ジョブ失敗、または失敗・再実行でデータ欠損・重複が起きうる（例: 大規模データの `collect()`、処理が失敗しても `job.commit()` まで到達してブックマークが進む、再実行で追記が重複する）
- **⚠️Medium**: 動くがコスト・実行時間が大きく悪化する（例: パーティションプルーニング漏れ、Python UDF、小ファイル大量出力）
- **ℹ️Low**: 影響は小さいが改善した方がよい（例: 不要な `toDF()` / `fromDF()` の往復）
- **💡Suggestion**: 品質・保守性の提案

### 5. まとめる

レビューの最後に以下を書く。

- 前提として置いた仮定（ジョブタイプ、バージョン、データ量）
- 重要度別の件数
- 最も効果の大きい改善 1〜3 点（どれから直すべきか）

問題が見当たらない観点まで列挙する必要はない。指摘ゼロなら、その旨と確認した主な観点を簡潔に書けばよい。
