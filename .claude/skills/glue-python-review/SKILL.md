# AWS Glue Python コードレビュー

Glue 上の Python コードは「1台のマシンで動く Python」として書くと、正しく動いても遅い・高い・OOM で落ちる、という壊れ方をする。
このレビューの目的は、**Spark の分散処理と Glue の機能に仕事を任せられているか**を確認し、そうなっていない箇所を是正することにある。
文法やスタイルの指摘は二の次でよい。データ量が 100 倍になったときに壊れる箇所を優先して見つける。

## レビュー手順

### 1. ジョブの前提を把握する

コードと周辺ファイル（IaC、ジョブ定義、README など）から以下を特定する。不明なものは推測した前提としてレビュー冒頭に明記する。

- **ジョブタイプ**: Spark ETL（`GlueContext` / `SparkSession`）か、Python Shell（pandas / boto3 中心）か。観点が大きく変わる
- **Glue バージョン**: 4.0（Spark 3.3 / Python 3.10）、5.0（Spark 3.5 / Python 3.11）など。AQE などの機能有無に影響する
- **入出力**: Data Catalog 経由か S3 直接か、ファイル形式、パーティション列
- **想定データ量**: 分からなければ「本番で数百 GB 規模になりうる」と仮定して評価する

### 2. 処理の流れを Driver / Executor の視点で追う

上から順に、各処理が **Driver で動くのか Executor で分散されるのか**、**どこで Action（実計算）が発生するか**を意識して読む。
Spark は遅延評価なので、`count()` や `show()` のような何気ない呼び出しが DAG 全体を再計算させることがある。

### 3. チェックリストで確認する

`references/glue-checklist.md` を読み、該当する観点を確認する。チェックリストは網羅を目指したものではなく、よくある失敗パターン集である。
リストにない問題でも「Driver にデータが集まる」「同じ計算が繰り返される」「読む/書くデータ量が必要以上に多い」に当てはまるなら指摘する。

### 4. 指摘を書く

各指摘は以下のテンプレートで書く。**改善後のコード例を必ず添える**。Glue 特有の問題はなぜダメなのかが直感的でないため、「何が起きるか（例: 全件が Driver に転送され OOM）」を具体的に説明すること。
レビューを読むのは Glue / Spark に不慣れな開発者である可能性が高い。「遅延評価」「シャッフル」「プルーニング」などの用語は初出で一言説明を添え、指摘が次に同じコードを書くときの学びになるようにする。

````md
## <!-- 指摘内容の要約 -->

- **重要度**: [ 🚨High / ⚠️Medium / ℹ️Low / 💡Suggestion ]
- **箇所**: `path/to/job.py:42`
- **観点**: <!-- 例: Driver 集約 / パーティション / ブックマーク -->

**詳細**

<!-- 何が問題で、データ量が増えたとき・本番で何が起きるか -->

**改善案**

```python
# 修正後のコード
```

**補足**

<!-- トレードオフ、前提条件、同様の箇所が他にあればそのパス -->
````

重要度の目安:

- **🚨High**: データ量増加で OOM / ジョブ失敗 / データ欠損・重複が起きうる（例: 大規模データの `collect()`、ブックマーク有効なのに `job.commit()` がない）
- **⚠️Medium**: 動くがコスト・実行時間が大きく悪化する（例: パーティションプルーニング漏れ、Python UDF、小ファイル大量出力）
- **ℹ️Low**: 影響は小さいが改善した方がよい（例: 不要な `toDF()` / `fromDF()` の往復）
- **💡Suggestion**: 品質・保守性の提案

### 5. まとめる

レビューの最後に以下を書く。

- 前提として置いた仮定（ジョブタイプ、バージョン、データ量）
- 重要度別の件数
- 最も効果の大きい改善 1〜3 点（どれから直すべきか）

問題が見当たらない観点まで列挙する必要はない。指摘ゼロなら、その旨と確認した主な観点を簡潔に書けばよい。
